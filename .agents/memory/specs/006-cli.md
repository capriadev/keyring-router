# kr CLI: one command to run and manage the gateway

Spec ID: 006
Status: pending
Branch: feature/v1-gateway
Depends on: spec 001 (the API), spec 002 (catalog), spec 005 (secrets).

## Objective

Give the product its own command. A user installs once, runs `kr serve`, and manages credentials, policies and models from the terminal when they do not want the UI. Every management command talks to the running gateway over its own HTTP API, so there is one source of truth and the CLI can never drift from the app.

## Placement

A new workspace `apps/cli`, named `@keyring-router/cli`, exposing the `kr` bin. `architecture.md`'s planned layout only lists `backend` and `frontend`, so this spec updates that layout line: the CLI is a thin client of the local API plus a process launcher, and it does not belong inside the backend app.

## Scope

In scope:

- `kr serve` launches the gateway in the foreground, with `--port` and `--db` overrides.
- `kr status` reports gateway health, version, database path and provider count.
- `kr credential add|list|show|validate|refresh|rotate|remove`, with the secret read from an interactive prompt or stdin, never as a plain argument in shell history.
- `kr policy allow|deny|list|remove`, using the same endpoints the UI uses.
- `kr models` lists the policy filtered models, with `--catalog` for the full discovered set and its exposure flag.
- `kr doctor` checks the environment: Node version against `.nvmrc`, pepper presence, database reachability, applied migrations, and whether Ollama or any local provider is answering.
- `kr version`.

Out of scope: installing the Windows service (spec 007), interactive TUI, shell completion and any network exposure beyond loopback.

## Design

- Argument parsing with the built in `node:util` `parseArgs`. No CLI framework dependency: the surface is small and the standard library is enough.
- `apps/cli/src/commands/<command>.ts`, one file per command, plus `client.ts` for the HTTP calls and `output.ts` for rendering. Human output by default, `--json` for scripting.
- Exit codes are meaningful: `0` success, `1` usage error, `2` gateway unreachable, `3` command rejected by the API.
- Secrets: `kr credential add` prompts without echo, and the value is only ever sent over loopback. It is never printed back, not even masked beyond the stored hint.
- `kr serve` starts the backend the same way `npm run start:prod` does, so there is no second launcher implementation.

## Acceptance criteria

- [ ] `kr --help` and `kr <command> --help` describe every command and flag.
- [ ] `kr status` against a running gateway prints health and version from the real API response.
- [ ] `kr credential add` stores a secret that never appears in the terminal output, in the shell history, or in a log line; a test asserts all three.
- [ ] `kr models` and `kr models --catalog` show exactly what the API returns, proven by comparing against a direct API call.
- [ ] `kr doctor` detects each broken precondition with a clear message: wrong Node version, missing pepper, migrated or unmigrated database, unreachable provider.
- [ ] Every command exits with the documented code for its failure class.
- [ ] `--json` output is valid JSON and matches the documented shape.
- [ ] The CLI adds no runtime dependency.
- [ ] An independent audit reproduces every criterion above.

## Risks

- A CLI that reimplements logic instead of calling the API would become a second system. The rule is absolute: management commands call the API, only `serve` and `doctor` touch the process and the filesystem.
- Secrets on the command line are a real leak vector, so the flag based path is refused by design.
