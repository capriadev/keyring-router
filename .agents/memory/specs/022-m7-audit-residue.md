# Residue of the M7 routing audit

Spec ID: 022
Status: pending
Branch: feature/v1-gateway
Origin: the independent audit of milestone M7 (spec 004) that ran this session. It reproduced every acceptance criterion from the spec on its own (backend 448 of 448, every workspace green, tsc clean, 27 end to end at the time), induced a failure per branch of the verdict, and confirmed the core mechanics over a real socket: the three modes, a user-ordered cascade that invents no target, lockout with recovery, no re-route after the first frame, and a secret-free observability endpoint. It found no blocker, one major and six minor defects, and read two criteria as partial. This spec records what it found. What was verifiable was fixed in the same session and is written down here too.

## Fixed in the same session, with the audit as the source

- D1 (major, dormant): the quota hold never expired. `toRoutingState` computed the bound with the read instant, so a window with zero remaining and no known reset slid forward on every request and never let the credential back in. Fixed: `QuotaRecord` was split into `QuotaWindow` (the stored window, no instant) and `QuotaRecord` (what is read, with `observedAt`), and the hold is now measured from `observedAt`, a fixed instant, with the verdict comparing the resulting absolute bound against the request clock. `toRoutingState` no longer takes a `now`, which the fix left dead. Red before green: anchoring the hold to the read instant failed the three quota cases. Dormant today because no production path writes a quota row yet (see D5-adjacent, below).
- Criterion 5 (partial): the documented ordering rule was wrong. `candidates.ts` said credentials are returned "by registration, then by id"; `CredentialsRepository.list()` orders by (`createdAt`, `namespace`). The comment is corrected and a tie-break test over the real repositories was added: two credentials registered at the same instant are ordered by namespace, and one registered later comes after both whatever its namespace.
- D8 (minor, documentation): the Status of spec 004 overstated its coverage. The counts for `chat.service` and `state.service` are corrected, and the endpoint's coverage is stated as it is: the two tests are `snapshot()` unit tests, with no dedicated controller spec and no end to end call to `GET /api/routing/state`.

## Open, and each with its reason

- D2 (major, a decision): a throw while resolving a later attempt aborts the whole list. In `chat.service.ts`, `resolveAttempt` and `translatedRequest` run outside the `try`, so a candidate that cannot be turned into a route (an untranslatable provider protocol, a credential gone between plan and resolve) fails the request even though a later attempt might answer. Whether a capability gap of one candidate is a skip or a failure is a decision the spec does not take. Closing it means deciding which resolution failures are skippable (provider and capability) and which are not (the client's body, translated after them), and moving only the first inside the loop.
- D4 (minor, a decision): a credential that answers 200 and then breaks the stream is never locked out. Only failures before the first frame are recorded, because `chat.service.ts` throws before `recordFailed` once the request is committed. A provider that opens a stream and hangs up repeatedly is never taken out of service. Whether a mid stream break should count, and toward which threshold, is a decision: the client may already hold a partial answer.
- D5 (minor, a decision and a scope item): quota is read but never written, and the degradation report is computed but never surfaced. No production path calls `saveQuota`, so the "quota exhausted is skipped" behaviour is exercised only by tests; feeding it means reading a provider's window (often in response headers, and often undocumented), which is per provider scope the design does not name. Separately, the spec's scope asks for "which credential carried the request and why the others were skipped"; `plan()` computes exactly that and only the all-failed error path consumes it, `RoutingOutcome` has a `'skipped'` member nothing writes, and no client reads the endpoint. Both wait for a decision on how far to feed and how far to surface.
- D6 (minor, correctness): the streaming envelope reports the first attempt's warnings even when a later attempt serves. `chat.service.ts` builds `warnings` from attempt 1's translation while the body is re-translated per attempt, so a request served by attempt 2 can carry a warning that describes attempt 1's model. `complete()` re-translates inside the loop and does not have this bug.
- D7 (minor, a behaviour change to state, written down so it is not a surprise): the routing state applies in every mode, so in `normal` a credential locked by an earlier run is refused with `all_attempts_failed` instead of being called and failing as `provider_failure`. Same HTTP status, different code. This is intended, because health should not be suspended for a direct request; if `normal` must reproduce today's behaviour including the ignore-health case, that is the change to make.

## Not blocking

None of the open items is a blocker. The core mechanics the milestone claims are sound and were reproduced end to end over a real socket. Each open item waits for the next touch of its file or a decision, whichever comes first.
